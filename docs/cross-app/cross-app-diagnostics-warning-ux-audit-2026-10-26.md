## Cross-app findings and candidate priorities

1. **Highest-priority source-confirmed ownership issue:** NarrativeLine assigns valid candidate warnings before replacement acceptance and leaves them after Cancel (N4). The current Timeline can therefore label a rejected candidate's warnings as ordinary “Import information”. Reproduce this exact sequence in isolated browser/DOM review before choosing the correction; preserve the current Dataset and candidate boundaries.
2. **Confirmed design gap:** raw Validator `code` and path are often the only specific import/export explanation (N2/N5, L1/L3/L5, P3). The stable machine contract is useful for support, but it does not by itself tell a general user whether work was changed or what action is possible. Add code-specific, capability-aware guidance only for verified remedies; keep diagnostic detail available. Do not convert every warning to a blocking alert.
3. **Confirmed, already OPEN:** LiaisonScape operation-specific failure details can be replaced by later current-Dataset revalidation; decide whether failed operation history must persist independently (L6). Separately fix candidate dialog code/path readability (L8) after approval. Neither changes the bounded D2 closure.
4. **Source-based risks needing reproduction:** NarrativeLine import-context warnings and failed Export issues can outlive a later edit because neither is keyed to a Dataset revision (N4/N5). ParameterPlotter transient operation notices clear on any later input/click (P7). Test whether a user loses needed recovery guidance or sees obsolete failure; do not label these confirmed defects yet.
5. **Application-specific continuity:** Hub does not observe recipient Handoff success (H2); review whether return/retry guidance is needed at the receiving application. Hub need not become a Validator UI. ParameterPlotter read-only/unsupported states and NarrativeLine supported authoring paths need different remedies from LiaisonScape coordinate refusal.
6. **Current accepted boundary:** LiaisonScape does not add ordinary UI warnings merely for recognized-but-unedited Extensions. Published Validator `0.7.0` retains Lighthouse JA's two technical warnings. Candidate `0.2.0` remains non-Stable; no suppression, dependency update, D1/D2 reclassification, or general preservation promise follows from this audit.

## Repair and Export feasibility

The Core requires unique IDs and resolvable Relation endpoints and says unknown fields/Extensions should be preserved whenever practical (`spec/core.md:143-176,232-250`). The Validator identifies errors/warnings by path and does **not** return repaired data (`e2r-validator/src/core-validator.js:24-100`, `docs/diagnostic-contract.md`). Existing application Export paths can validate, serialize, and in narrow documented cases complete a Specification declaration; they are not general-purpose repair engines. NarrativeLine's recognized legacy-date migration is an existing import behavior with a warning and unchanged source file, not proof that arbitrary invalid JSON can be safely repaired.

| Class | Examples supported by current contract | Feasibility and safe boundary |
| --- | --- | --- |
| A — semantic-preserving automatic candidate | No malformed-Dataset transformation was proven safe for all four apps. Formatting an already parsed, valid JSON copy may be semantics-preserving but does not cure Core/Extension errors. | **No automatic repair class is approved.** A later design must demonstrate exact before/after semantic equivalence and validate the isolated output. |
| B — Human choice required | Duplicate IDs, unresolved Relation endpoints, conflicting Specification `uses`, invalid recognized Extension fields or versions. | User must choose which object/reference/version/meaning is intended; preview the full affected graph and diff. Do not invent IDs or values silently. |
| C — missing information | Truncated/unparseable JSON, absent objects/IDs/targets, unknown intended timestamp, Coordinate, or Extension version. | Full repair cannot be established from the input alone. Any recoverable fragment is **partial rescue**, with omitted content explicitly listed. |
| D — preserve, no repair | Unknown Extension or unknown Core field that is merely warned about; exact version unknown but Dataset remains valid; known data an app does not present/edit. | Keep opaque content where the specific path demonstrably preserves it. Never present warning removal or guessed version as repair. Inform user only if actual work/safety is affected; retain technical diagnostics. |
| E — loss/meaning change risk | Dropping unknown payload, removing a Relation to silence an unresolved endpoint, changing a Version string without evidence, discarding malformed fragments, auto-writing coordinates, or replacing a Workspace. | Prohibit silent transformation. Require explicit choice, original preservation, visible diff, revalidation, and unambiguous partial-result labeling. |

An independent “Repair and Export” design could accept a byte-preserved source copy, parse or classify it, produce a separate candidate with provenance and a machine-readable/EN/JA diff, run the pinned Validator on that candidate, show remaining errors/warnings and omissions, and require explicit user approval before downloading. It must not mutate the active Dataset, overwrite browser storage, bypass replacement/cross-context safety, treat download initiation as durable storage, or claim completeness when only a subset was rescued. The first design gate should choose a narrowly evidenced input class and decide who owns repair semantics; current evidence does **not** justify implementation or a universal repair promise.

## Proposed common UX principles — not adopted

1. Present **condition + effect + next safe action + verification point** for a user-actionable problem. For example, distinguish “Export was refused; current Dataset remains open” from “browser was asked to download; verify the file.” Include a no-in-app-fix path when appropriate.
2. Maintain separate identities and lifetimes for **current Dataset validity**, **acquisition candidate**, **operation attempt**, **draft field**, and **persistence/recovery risk**. A committed edit may refresh current validity; it must not silently rewrite history of a failed save. Cancel closes a candidate; it does not repair it. A new successful action does not establish earlier download or storage success.
3. Make persistent unresolved loss/unsaved-work risk visible until the corresponding state is actually verified safe. Allow a transient message to be dismissed without equating dismissal to resolution. Key revision-specific issues to the relevant Dataset revision or label them as an earlier attempt.
4. Keep raw Validator code/path/severity in expandable technical detail. Promote to an ordinary prominent warning only when the current application operation or user's decision is affected. Never suppress or change valid Validator diagnostics solely for visual tidiness.
5. Suggest only an operation proved to address the identified cause in that app. “Move an Entity”, “save coordinates”, “retry”, and “choose another Dataset” are not interchangeable. When there is no safe current-UI fix, say so and preserve access to the source/Export where permitted.
6. Use natural EN/JA copy for impact and action, stable machine identifiers for support, `role=alert` for immediate blockers and appropriate `status`/`aria-live` for nonblocking updates. Review focus after dialogs and ensure repeated alerts do not drown out unresolved safety state. Exact component, layout, and persistence mechanism remain application-local.

## Human design gates

- **A — principles:** Adopt, revise, or reject the six proposed principles as cross-app application guidance. This would be an application UX decision, not a Core or Validator change.
- **B — classification/lifetime:** Decide whether current-state, candidate, operation-attempt, draft, and persistence notices require distinct revision ownership; specifically decide LiaisonScape operation-specific failure lifetime. Keep technical Diagnostics even if ordinary presentation changes.
- **C — first implementation:** Recommend first reproducing NarrativeLine N4's source-confirmed candidate-warning ownership path, then deciding its correction. LiaisonScape's OPEN candidate dialog readability and operation-lifetime issue are next independent slices; reproduce NarrativeLine N5 and ParameterPlotter P7 before treating them as defects. Select an app and bounded acceptance criteria before code work.
- **D — Repair and Export:** Recommend a separate design study only, beginning with one exact diagnostic/input class and a non-destructive proof. Do not approve a repair engine, automatic data rewrite, or changed normal Export semantics from this audit.
- **E — publication:** Review this local document for a bounded documentation commit; authorize any Push separately with an exact range. No application implementation, new Human Acceptance, release, or deployment is implied.
