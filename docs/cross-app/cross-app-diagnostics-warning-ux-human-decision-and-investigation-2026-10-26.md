## Human adoption — 2026-10-26

**A — common application UX principles.** For a user-actionable problem, explain its cause, effect, safe next action, and how to verify resolution. Distinguish Current Dataset, Candidate, Operation, Draft, and Persistence notices. Keep unresolved save failure, unsaved work, and data-loss risk visible until safety is verified; dismissal is not resolution. Preserve legitimate Validator Diagnostics while prioritizing work-relevant notices in ordinary views. Recommend only an action proven to address the cause in that application, and state accurately when no in-app remedy exists. Provide comprehensible EN/JA explanations and access to technical Code, Path, and Severity where needed. These are cross-app **application UX design principles**, not Core, Extension, or Validator Diagnostic Contract changes, and do not require one component or state-management implementation.

**B — attribution and lifetime.** Current Dataset diagnostics belong to its current state; Candidate diagnostics belong to the candidate and must not appear as current-Dataset problems after Cancel. Operation failures describe that operation's result and must not become misleading after later actions. Draft issues follow the applicable input state. Unresolved Persistence or data-loss risk cannot disappear as a mere transient notice. Technical Diagnostics and ordinary notices may have different lifetimes. Exact duration, dismissal, layout, and state machinery remain application-local. LiaisonScape's operation-specific failure lifetime is still an OPEN design and Human Browser review matter; this adoption does not close it.

**C — priority.** First investigate NarrativeLine N4's candidate-warning ownership, then design an approach for LiaisonScape L3's Lighthouse EN/JA technical warnings. This prioritization does not authorize Runtime fixes. NarrativeLine N5, ParameterPlotter P7, LiaisonScape L6 and L8 retain their separate evidence and status in the audit.

**D — Repair and Export.** An independent design study is authorized. No repair engine, automatic correction, or ordinary Export behavior change is authorized. Preserve the original, show explicit differences and omissions, revalidate any separate output candidate, and require Human choice where meaning or data could change. It is not a Public Beta prerequisite.

**E — documentation.** Human authorized a local Documentation Commit limited to the preceding comprehensive audit file. This decision record and Roadmap synchronization are separate uncommitted changes; their Commit and any Push require separate authorization. Existing Acceptance and Publication Closure remain bounded by their own records.

## NarrativeLine N4 — investigation

Current source: `e2r-narrative-line/src/App.tsx` stages the candidate and calls `setImportWarnings(warnings)` in `handleOpenDataset` before replacement acceptance (`:706–724`). `handleCancelReplacement` clears the candidate but not those warnings (`:730–737`). `TimelineScreen.tsx` renders `importWarnings` as ordinary “Import information” without candidate attribution (`:539–592`). A successful immediate acceptance passes its warnings through (`App.tsx:719`), but the guarded Discard and Export-and-Continue paths call `acceptStagedDataset()` with the default empty warning list (`:725–749`), so warnings may disappear when B actually becomes current. A failed cross-tab replacement write returns before changing the Dataset, yet the staging-time warning write has already happened (`:649–724`). Invalid Import does not call `handleOpenDataset` (`:758–770`). These are source observations, not claims that every acquisition route has been exercised.

An isolated jsdom run of the production App via Vite SSR used only a disposable origin, in-memory test Datasets, and the test environment's localStorage. Current Dataset A had an unsaved title edit. Candidate B was Core-valid and contained a deliberately unknown Extension, yielding `unknown_extension`. After B was selected, the replacement dialog and “Import information” both appeared. After Cancel, the dialog closed; A remained visible and stored, B was absent, but B's `unknown_extension` remained in the Timeline's “Import information”. The probe passed **1/1** and its temporary test file was removed. This reproduces the specific attribution error in isolated DOM, not a real-browser or Human Browser Acceptance result. No user's Workspace or Dataset was used.

The direct cause is one `importWarnings` state shared by an accepted Dataset and an unaccepted Candidate, with a write at staging time and no Cancel cleanup. The default empty list in guarded acceptance is a related source-confirmed loss of B's warning attribution; its user-visible effect remains to be reproduced separately. The narrow correction to consider is separate Candidate warning ownership from accepted/current import information. Candidate warnings may be shown in the replacement decision context; Cancel discards that presentation without changing A; Accept promotes B's relevant warnings only after the guarded replacement succeeds. A failed safety write retains the candidate's warning context without attributing it to A. Invalid acquisition remains an acquisition error. Verify repeated candidates, warning-free candidates, Cancel, guarded Accept, Export-and-Continue failure, and cross-tab refusal against Dataset Replacement and Cross-Context Workspace Safety. Runtime design and implementation require a later Human decision.

## LiaisonScape L3 — evidence and design options

The installed published Validator `0.7.0` was run against the bundled Lighthouse Restoration **EN and JA** JSON files. Both returned `valid: true` and exactly two `warning` Diagnostics: `unknown_extension` at the Dimension Assessment payload and `specification_unavailable` at its Specification `uses/3/extension`. LiaisonScape pins `0.7.0`, accepts the valid Dataset, and places these diagnostics in its ordinary on-screen `Validation diagnostics` list with severity, raw Code, and Path (`src/App.tsx:1321–1331,2560–2570`). This is a service/source confirmation, not a new real-browser observation. It does not establish full Dimension Assessment validation or preservation for arbitrary edits and Datasets.

The 2026-10-24 [recognition decision](../liaisonscape/liaisonscape-dimension-assessment-recognition-audit-2026-10-24.md) separates Extension recognition from display/edit capability; lack of LiaisonScape editing alone needs no ordinary warning. The [compatibility decision](../liaisonscape/liaisonscape-validator-dimension-assessment-compatibility-review-2026-10-24.md) retains Validator `0.7.0` and its legitimate warnings for now. The bounded Lighthouse preservation acceptance covers only its reviewed path. The new A/B UX decision is consistent with these boundaries: ordinary user prominence can follow an actual effect on work while the technical diagnostics remain available, accurate, and attributable to the current Dataset.

Design option for Human selection: keep the complete Validator result in technical Diagnostics, and give the ordinary Home/graph view a separate, capability-aware notice only when validation blocks Import/Export, an operation is refused, preservation is uncertain, or a compatibility choice is required. For these two current Lighthouse warnings, a discoverable technical-detail entry can explain in EN/JA that the installed Validator cannot identify this Candidate and exact specification version, that the Dataset loaded, and that LiaisonScape does not edit Dimension Assessment; it must not promise universal preservation or say the warning was repaired. Whether technical detail is collapsed, moved to a dedicated Diagnostics view, or linked contextually is an application-local design decision. A counteroption is keeping the present always-visible list; it preserves visibility but leaves the observed ordinary warning confusion. **Neither option authorizes code or suppression.**

Before a UI choice becomes an implementation proposal, define classification for mixed warnings, unsupported versions, real validation errors, refused Export, and uncertain preservation. Test both locales, keyboard and screen-reader access to technical details, and whether severe issues stay prominent. If the desired outcome instead requires changing Validator version or diagnostic behavior, return to Human: a newer Validator can turn currently accepted malformed Candidate data into errors and change Import/Export gates. No dependency change is part of this decision.
