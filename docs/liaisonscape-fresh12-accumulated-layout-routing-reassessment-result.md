## Result

The strongest current development direction is not a new layout algorithm.
It is a bounded combination of two already available mechanisms:

1. retain the current Product degree-centered ring seed and settling kernel,
   but test a moderately larger existing `nodeClearance` configuration; and
2. after placement, reuse the current ordinary-route candidate space with the
   previously researched true-crossing / final-presentation safety ordering.

On Apollo 11 EN, `nodeClearance=120` with the existing three settling
iterations reduced the Product-seed control's crossings from `6` to `4` and
removed several measured label/corridor conflicts. In that geometry, one
current-space route candidate (`entity-4`, offset `84`) reduced crossings from
`4` to `3` without worsening any measured collision count or identity relative
to the `120`-clearance state.

This is **promising bounded evidence**, not a Production parameter selection.
The browser image still contains material relation-label and edge-corridor
congestion. The exact value `120`, the route offset, cross-locale behavior, and
cross-fixture behavior remain unaccepted.

## Current Apollo mechanism assessment

### PROVEN

- The Product-seed control uses `solveAutoLayout` with a degree-centered ring
  seed and three settling iterations.
- Attraction has no target length and acts at every nonzero connected
  distance. Repulsion acts only below `nodeClearance` and is not a hard
  separation constraint.
- Apollo's initial, zero-iteration seed has minimum Node distance `132.3`.
  After one iteration it is `113.8`; after three it is `86.1`. The Product
  control therefore has active repulsion, but attraction and sequential
  bounded updates still compress the closest pair below the 96-unit setting.
- The current Product router does not directly score true transverse
  crossings. Its candidate space nevertheless contains crossing-reducing
  alternatives.
- The parent/branch-sector Lighthouse result is excluded by its own Apollo
  topology guard, and the shared-neighbor displacement is an Apollo no-op.

### STRONGLY SUPPORTED

- Apollo's remaining visual problem is mixed: spacing and routing arbitration
  both matter. Placement alone and routing alone each leave a material
  trade-off.
- A moderate spacing increase can create a geometry in which the existing
  route candidate space has a safer crossing-reducing choice. This interaction
  is stronger than either isolated change in the tested Apollo state.
- The present relation-label congestion cannot be fixed by viewport fit alone;
  the measured fit is already above the minimum and the conflicts occur in
  graph space.

### UNRESOLVED

- Whether `nodeClearance=120` generalizes to JA and the required common fixture
  roles. The exact value is not selected.
- Whether the route candidate found by the bounded oracle can be selected by a
  deterministic, efficient Product objective without manual offset injection.
- Whether label/corridor quality needs a bounded route/final-label coordination
  pass, a placement change, or both.
- Whether initial placement and explicit Auto Layout should share the same
  spacing configuration.
- Whether fit should include route and label bounds after geometry quality is
  improved.

The experiment held the Apollo 11 EN fixture, Product graph construction,
three-iteration settling mechanics, Product routing candidate set, label
derivation, and `800 x 500` fit path fixed unless a row explicitly changes one
configuration. Metrics are diagnostic and not acceptance thresholds.

collision classes, while creating one Node-label/Relation-label identity
(`columbia | entity-10`).

### Route-candidate reuse

On the `96` control, all 363 one-route candidates were evaluated with a fresh
downstream Product routing and label pass:

- 67 reduced the crossing count;
- none was non-worse across the measured collision classes;
- the strongest (`entity-5`, current `-84` to `+84`) reduced crossings
  `6 -> 3`, but created `columbia | entity-4` as a Node-label/Relation-label
  conflict.

On the `120` geometry, the same 363 candidates produced:

- 43 crossing-reducing candidates;
- exactly one candidate non-worse across all measured collision counts and
  identities; and
- `entity-4` at offset `84` reduced crossings `4 -> 3` while retaining the
  `120` state's collision inventory.

The combined state has:

| Metric | Product-seed control | `clearance=120` + route candidate |
| --- | ---: | ---: |
| Node extent | `288.7 x 325.2` | `360.9 x 406.5` |
| Minimum Node distance | `86.1` | `108.5` |
| Route median | `86.2` | `172.7` |
| Route maximum | `235.8` | `325.1` |
| Crossing pairs | `6` | `3` |
| Fit scale | `0.7914` | `0.6547` |

The larger route lengths and lower fit scale are expected costs of increased
spacing. They remain far from Fresh12 FP1's `6036 x 6036`, maximum route
`7862.6`, and clamped `0.1` fit.

## Recommendation

Classification:

`ACCUMULATED METHOD IS PROMISING; ANOTHER BOUNDED COMPARISON IS REQUIRED`

The next checkpoint should preserve the current Product-seed control and test
the combined mechanism on the same frozen EN/JA fixture roles, especially
Apollo, Lighthouse, Ashen Crown, Titanic, and one sparse/control graph. It
should:

1. treat `nodeClearance` as a sensitivity range, not promote `120` directly;
2. use the existing route candidate set;
3. require true-crossing improvement to be non-worse under exact final
   Node/label/route collision identities;
4. include Early Visual Smoke Check before any large evidence matrix; and
5. stop before Product adoption if locale or fixture behavior reverses.

If the common-fixture comparison does not retain the interaction, a new
topology-aware layout design becomes justified. The rejected shared-neighbor
and unguarded parent-sector implementations should not be revived unchanged.
