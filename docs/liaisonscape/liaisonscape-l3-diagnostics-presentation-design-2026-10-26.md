# LiaisonScape L3: technical Diagnostics presentation for Public Beta

Date: 2026-10-26 JST

Status: **IN-CONTEXT TECHNICAL DISCLOSURE HUMAN-SELECTED / COPY AND APPLICABILITY DESIGN OPEN / RUNTIME IMPLEMENTATION NOT AUTHORIZED** (2026-10-27). This document records an application-local presentation choice for existing Diagnostics. It does not modify Validator `0.7.0`, its Diagnostic Contract, its severity, the Dataset, the D1/D2 bounded closures, or the [2026-10-24 LiaisonScape recognition and retention decisions](liaisonscape-dimension-assessment-recognition-audit-2026-10-24.md).

## Human presentation selection — 2026-10-27

Human selected the first of the three proposed approaches: **brief user-facing explanation in the ordinary view, with technical Diagnostics available through an in-context expandable detail**. The always-visible technical list and dedicated Diagnostics page were not selected. This chooses the information hierarchy and access pattern, not a fixed component, placement, EN/JA text, prominence algorithm, preservation guarantee, or Runtime implementation. The adopted cross-app warning UX principles still require legitimate Validator findings and actual validation/export refusals or data-loss risks to remain visible at the appropriate layer. Recognized but uneditable content alone is not a reason for a prominent ordinary fault notice. Current, Candidate, and Operation attribution remains distinct.

## Evidence and boundary

The [cross-app audit](../cross-app/cross-app-diagnostics-warning-ux-audit-2026-10-26.md) records L3 and the [2026-10-26 Human UX adoption](../cross-app/cross-app-diagnostics-warning-ux-human-decision-and-investigation-2026-10-26.md) distinguishes ordinary notices from technical Diagnostics. Installed published Validator `0.7.0` returns `valid: true` for both bundled Lighthouse Restoration EN/JA files, with `unknown_extension` at `/extensions/draft.github.sukoyaka-dopeness.dimension-assessment` and `specification_unavailable` at its Specification `uses/3/extension`, both severity `warning`. They describe the installed Validator's recognition limit; they do not, alone, establish corruption. They also do not prove full preservation across arbitrary operations. The two codes are currently displayed in a normal on-screen `Validation diagnostics` list (`e2r-liaison-scape/src/App.tsx:2560–2570`). The replacement candidate has a separate warning disclosure in `DatasetReplacementDialog.tsx`; Import validation errors are refusal notices; Export revalidates and can refuse on errors. Current Dataset Diagnostics refresh after committed changes is the bounded D2 closure. Operation-specific Diagnostics lifetime remains separately OPEN.

## Selected information hierarchy; detailed design proposed

1. **Immediate ordinary notice for an actual effect.** A rejected Import/Handoff, blocked Export, failed save, lost or uncertain persistence, refused edit, or demonstrated preservation limit keeps its existing operation-specific result and safe recovery guidance. A real Validator `error` remains prominent, with its exact Code/Path available. A warning that affects a decision or operation is explained in plain EN/JA with the affected Dataset or operation named. Do not infer a remedy from code alone.
2. **Always discoverable technical Diagnostics.** When the Current Dataset has any diagnostics, show a consistently placed, keyboard reachable control such as **“Dataset diagnostics (2)” / “Datasetの診断情報（2件）”**. Opening it reveals every current Validator item, unchanged severity, Code, Path, and any available message, grouped under “Current Dataset”. The closed control has a neutral visual treatment when findings are informational for the current work; its count is not a claim that all items are harmless. Keep it findable without scrolling to a hidden footer. Do not remove any item or mutate the Validator result to produce the ordinary summary.
3. **Explain the precise Lighthouse case within detail.** For the reviewed EN/JA Lighthouse files and only when the exact known codes, paths, declared `0.2.0` version, and `valid: true` agree, add plain language adjacent to those two technical items. Suggested EN: “This Dataset opened. The installed Validator cannot identify this Dimension Assessment version. LiaisonScape does not edit these values. This notice does not confirm their safety in every edit or Export.” Suggested JA: “このDatasetは開けました。現在のValidatorは、このDimension Assessmentのバージョンを認識できません。LiaisonScapeではこの値を編集できません。この表示は、すべての編集や書き出しでの完全な保全を保証するものではありません。” Treat this as explanation, not a claim that the Validator recognized the Extension or repaired the Dataset. A general unknown Extension must not inherit this Lighthouse-specific text.

The in-context disclosure is the **Human-selected presentation approach**, not a requirement to use a particular HTML component. A permanently visible technical list and a dedicated Diagnostics page were considered but not selected. This decision does not settle exact prominence for mixed findings or the detailed layout; those remain design work before implementation.

## Attribution and mixed cases

| State | Ordinary layer | Technical layer |
| --- | --- | --- |
| Current Dataset with only the exact reviewed Lighthouse warnings and no affected operation | No corruption-style banner. Neutral diagnostics entry and bounded explanation in detail. | Preserve both warnings verbatim under Current Dataset. |
| Current Dataset with other or mixed warnings | Decide prominence by verified effect and preservation uncertainty; do not automatically mark unknown data safe. | Show all items and their actual severity/path. Lighthouse explanation applies only to the matching pair. |
| Current Dataset with a validation `error` | Prominent current-state error; state the affected operation and safe recovery. Never conceal Export refusal. | Show all errors and warnings, including the Lighthouse pair if present. |
| Replacement Candidate | Candidate-specific information in the existing dialog. Cancel removes candidate context and retains Current Dataset diagnostics. | Candidate findings remain separately labelled and do not replace Current Dataset findings before Accept. D1 remains bounded. |
| Import/Handoff refusal or Export/save/coordinate operation failure | Operation result remains visible with its real effect and retry or preservation guidance; a later Dataset revalidation must not falsely imply that the failed operation succeeded. | Retain available operation details with operation attribution. Their lifetime is the separate OPEN L6 decision, not closed by L3. |

Unknown and unsupported Extensions are not automatically invalid. Equally, an unrecognized payload has not been semantically checked by this Validator. If an edit/export path cannot establish preservation, disclose the limit at that operation rather than using a generic “safe” badge. Never convert a `warning` to success, skip validation, or claim the limited LS-DA-PRESERVE2 acceptance applies to every Dataset and operation.

## Accessibility and acceptance criteria for a later implementation

- The Diagnostics entry is visible in EN/JA whenever the Current Dataset has findings; its accessible name states the Dataset scope and count. Enter/Space opens it; Tab reaches all controls; Escape or an explicit close control returns focus predictably. Details are readable in document order and can be copied for support. A collapsed detail does not hide a blocking error or unresolved loss risk from the ordinary layer.
- Screen readers receive a concise update when a new blocking condition appears. Ordinary `alert` or live-region behavior is reserved for changes requiring immediate attention; opening the technical list does not reannounce every old warning as a new failure. Counts and labels refresh with the committed Dataset revision, while a pending Candidate stays separate.
- EN/JA wording is tested on Lighthouse EN/JA, a genuinely unknown Extension, an unsupported version, mixed warnings, and a real error. Code, Path, and Severity remain exact and accessible in each case. The known-case explanation is shown only for verified code/path/version conditions.
- Import/Handoff refusal, Export refusal, failed coordinate save, replacement Cancel/Accept, and committed Dataset edits retain their existing safety behavior and bounded D1/D2 re-evaluation. No new state transition, hidden validation, or Dataset mutation is introduced by presentation work.
- Browser review includes normal and narrow widths, keyboard-only use, assistive technology inspection, both locales, and mixed diagnostics. Automated tests cover classification and state attribution, but cannot by themselves establish Human Browser Acceptance.

## Remaining design and Human decision boundary

The ordinary/technical presentation approach is selected. Precise EN/JA copy, mixed-warning prominence, preservation-uncertainty explanation, screen applicability and placement, and the classification owner still need design resolution or Human approval where material. L6 operation-specific lifetime and L8 candidate-dialog Code/Path readability remain separate follow-ups. Any Validator update, diagnostic suppression or severity change, or Runtime implementation requires its own authorization. Public Beta GO/NO-GO remains independent.
