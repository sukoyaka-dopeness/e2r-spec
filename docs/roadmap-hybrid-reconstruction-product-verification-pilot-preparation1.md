## Purpose and authority boundary

This document prepares the first claim-level pilot for the selected hybrid
Roadmap reconstruction approach:

- **B where proven:** a current planning consequence and its latest authority
  are sufficiently clear to synthesize later, while dated progression may be
  delegated to the existing broad History unit;
- **A where ambiguous:** the current consequence is clear, but heading,
  provenance, or historical/current separation is not safe enough for removal;
  retain the heading and compress only to a scoped consequence plus pointer;
- **HOLD where unresolved:** authority, status, scope, or current consequence
  is not uniquely established.

The pilot is limited to the Product-authoritative verification execution and
budget sequence in the Roadmap's Initial Layout region. It does not choose a
new Product status, budget, SLA, provider, solver, Worker adoption, visual
acceptance, or release position. It does not edit `docs/roadmap.md`, any
Roadmap History file, or application source.

The Roadmap remains the sole current-planning authority. The result documents
listed below remain evidence authorities; they are not replaced by this
manifest. The existing broad
[Layout and Auto Layout chronology](roadmap-history/liaisonscape-layout-and-auto-layout-chronology.md)
is the only proposed history destination for dated Initial Layout material.

## Current planning synthesis that must survive

The following is the minimum current-planning set identified by the evidence.
It is a synthesis target, not a replacement text for the Roadmap:

1. Fast deterministic Initial Placement plus explicit High-quality Auto
   Layout remains a **provisionally adopted execution direction** only.
2. The lifecycle contract is closed with corrections for snapshot identity,
   cancellation/staleness, preview isolation, accept/reject, revert, and
   explicit persistence. This does not mean the quality solver or Product
   integration is accepted.
3. Product-authoritative route, Relation-label, and Node-label accumulator
   seams and their full resumable orchestration have exact-equivalence and
   fail-closed evidence within stated controls. They are execution evidence,
   not a Product-wide performance SLA.
4. The tested bounded scaling envelope is evidence for the named workload
   envelope only. It does not establish an unbounded Product budget.
5. The Product-wide verification budget, hard production slice contract,
   quality solver, Product integration/default, production provider, Adaptive
   Cascade, and Human Review remain separate unresolved boundaries as stated
   by the latest applicable authorities.
6. Candidate-generation quality, cheap screening, multi-stage probing,
   boundary completion, visual quality, and Worker/provider execution are not
   interchangeable responsibilities. They remain outside a pure verification
   budget synthesis unless a later manifest proves otherwise.

## Proposed reconstruction boundary

The first safe pilot is not “all verification headings.” It is a bounded
claim family:

```text
PV-01 / PV-02
  -> provisional execution direction and corrected lifecycle boundary
PV-03 / PV-04 / PV-05 / PV-06 / PV-07 / PV-08
  -> Product-authoritative verification seam and execution evidence
PV-09 / PV-10
  -> current budget qualification and explanation of why no arbitrary split is adopted
```

PV-11 through PV-14 should remain outside the first pilot unless a subsequent
Human-reviewed manifest splits candidate-generation/quality, provider
execution, and Worker/application implementation into their own responsibility
groups. This boundary prevents a compact Roadmap summary from incorrectly
claiming that an execution seam is a Product feature, provider, SLA, or visual
acceptance.

If Human later approves **B** for the PV-01–PV-10 claim family, the proposed
current summary should retain only the minimum planning synthesis above. The
original Roadmap wording should be copied to the existing broad Layout/Auto
Layout History in source order with its date, status language, and authority
links preserved. No new checkpoint History file is needed.

If Human instead approves **A** for any member, retain its heading and replace
only the body detail with: current disposition, operative boundary, latest
authority link, and a History/evidence pointer. A heading should not be removed
merely because its generated anchor appears unreferenced.
