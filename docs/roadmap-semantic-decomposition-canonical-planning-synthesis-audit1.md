## Semantic responsibility test

For each prospective claim, the next implementation gate must distinguish:

| Information | Primary responsibility | Roadmap treatment if later approved |
| --- | --- | --- |
| Current priority, execution dependency, blocker, resume condition, explicit deferral, pending Human decision | Roadmap current planning | Keep one scoped canonical statement, with the relevant evidence link. |
| Adopted design or bounded Human acceptance | Named decision / acceptance authority | Retain the current consequence and precise limit; do not infer wider adoption. |
| Implementation, tests, diagnostic measurement, correction, and failed candidate | Application source and dedicated result/audit | Link to evidence; keep only a measurement that still defines an operative gate. |
| Dated `next`, `OPEN`, `HOLD`, test count, or intermediate interpretation | Roadmap History and the dated dedicated result | Preserve wording, order, status, and provenance as the *then-current* snapshot. |
| Exploratory hypothesis without an active dependency | Research | Keep a Roadmap pointer only when its deferral, trigger, or evidence gate constrains planning. |
| Core / Extension / schema meaning | Normative artifact | Do not derive or revise it through Roadmap compression. |

The test is the *responsibility of each claim*, not its date, length, or
heading. A block can contain several rows of this table. A later result may
supersede an earlier next step without erasing the earlier experiment, and a
formal release closure does not close a separate quality or runtime gate.

## Materially different reconstruction paths for Human review

| Path | Roadmap result | Main advantage | Main cost / gate |
| --- | --- | --- | --- |
| **A. Keep checkpoint headings, compress their bodies** | Preserve dated H3 and anchor identity; replace duplicate measurements/old next-step prose with a short scoped disposition and dedicated authority link. The parent retains canonical current status. | Lower anchor and provenance risk; can proceed in bounded responsibility groups. | The outline still has many checkpoint headings, and a reader may still mistake a sequence of old dispositions for current order. Every shortened body still needs latest-authority reconciliation. |
| **B. Synthesize current claims, delegate dated progression** | Keep `docs/roadmap.md` and its Current Initial Layout parent as the sole planning entry. Put current status, accepted limits, dependencies, resume conditions, and Human decisions in a small number of responsibility summaries. Preserve the original dated Roadmap wording/order/provenance in the existing broad Layout/Auto Layout History, with dedicated result links; remove redundant H3 only after inbound-reference checks. | Addresses both body length and outline density. The 1,905-line / 77-H3 band is the principal gross surface for possible reduction. | Highest status/anchor/provenance risk. The band contains current hypotheses and acceptance boundaries, not just history. History would grow; the net Roadmap saving cannot be promised before a paragraph-level manifest. |

Neither path is selected by this audit. The 1,905 lines are a **gross audit
surface**, not an approved deletion amount or a net savings estimate. A
hybrid sequence is possible: reconcile current claims once, then apply A to
ambiguous groups and B only to groups whose historical/current boundary is
proven. This would retain the existing broad History structure rather than
create a new taxonomy or a second planning authority.

## Implementation-preparation gate and Human decisions

Before changing the Roadmap, create a claim-level manifest for the chosen
responsibility group. Each statement needs: its current Roadmap location,
latest applicable decision/result/acceptance authority, exact current
consequence, historical text destination if any, and `KEEP / POINTER /
HISTORY / HOLD` disposition. The order of later authorities matters: a
diagnostic correction, source implementation, Human acceptance, and public
release closure are different events. A current consequence with no safe
dedicated owner stays in the Roadmap. Original dated text moved to History
must retain its source order and provenance.

The minimum Human structure choices are:

1. Choose whether to retain the 77 checkpoint headings as compressed pointers
   (A), or to use a canonical current summary plus existing broad History for
   safely historical members (B). A hybrid requires an explicit boundary.
2. Approve the current-planning responsibility map for Initial Automatic
   Display, Explicit Auto Layout, Product-owned presentation, Initial Layout
   research, PR-3 Browser Evidence, quality freeze, and release status. This
   includes resolving which dated `priority`, `provider`, and `release
   blocker` phrases are historical and which still have a scoped current
   consequence. Do not infer the map from a single old result.
3. If headings are removed or moved, approve the exact manifest and reference
   repair under the existing workspace-inbound-anchor policy. Preserve the
   Current Initial Layout parent anchor: the [Layout History](roadmap-history/liaisonscape-layout-and-auto-layout-chronology.md)
   points back to it. The canonical workspace search also found references to
   the status index, reconstruction parent, E2R-wide/Hub parents, and selected
   Relative Time child headings. A literal `roadmap.md#` search did not show a
   direct reference to the 77 dated H3s, but this is not proof about every
   link form or external deep links; recheck the exact final manifest.

An initial implementation preparation could isolate the Product verification
execution/budget sequence as a pilot. Its dedicated records include
[scaling/main-thread viability](liaisonscape-product-authoritative-verification-scaling-envelope-main-thread-viability1-result.md)
and the later [verification architecture decision](liaisonscape-product-verification-execution-architecture-decision1-result.md).
That pilot should first determine the *current* execution consequence and
correction order; it should not inherit a dated `next` or promote a diagnostic
budget to a Product SLA. Further groups can follow only after the same check.

No roadmap body, heading, anchor, History, Research, application, schema, or
specification content is changed by this audit. The next actual synthesis or
migration is a separate Human-reviewed checkpoint.
