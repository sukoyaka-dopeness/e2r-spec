the screen reported `unknown_extension` and `specification_unavailable` for
Presentation. Its installed dependency was
`@sukoyaka-dopeness/e2r-validator@0.2.0`, which predates the accepted local
Presentation support. The source/sample is not defective; the consumer package
artifact is stale.

## Published package state and local delta

The published/public 0.3.0 line lacks the Presentation validator module in the
public source. Local `4f5001e` adds that consumer-visible Extension validation
capability; local `231ab2f` registers its exact ID/version with Specification
local support. The public API remains compatible: both LiaisonScape and
NarrativeLine import only `validateDataset(value)` from the package, and local
HEAD retains that export and signature.

This is `FEATURE-like`, not a narrow patch correction: a new Extension
validation capability is being made available to package consumers. It is not
breaking-like because the existing API and valid Core behavior remain
compatible.

## Version alternatives

- Reusing `0.3.0` is rejected. Published npm versions are immutable in the
  ordinary workflow, and the same version must not identify materially
  different bytes.
- `0.3.1` is rejected as too weak for the complete new Presentation capability
  introduced after the public 0.3.0 source.
- `1.0.0` is rejected. This work does not establish a stable 1.0 contract.

### Selected Validator package version

`VALIDATOR-VERSION-0.4.0`.

This is the next pre-1.0 minor release and requires deliberate consumer opt-in
to the new supported Extension capability.

## Consumer range policy

- LiaisonScape future dependency: `@sukoyaka-dopeness/e2r-validator: ^0.4.0`.
- NarrativeLine future dependency: `@sukoyaka-dopeness/e2r-validator: ^0.4.0`.

Both consumers must move to the first package containing the accepted behavior;
NarrativeLine is included even though its current range is newer than
LiaisonScape’s, so both Public Sample participants use one known contract.

For npm 0.x caret ranges, `^0.2.0` means `>=0.2.0 <0.3.0`, and `^0.3.0`
means `>=0.3.0 <0.4.0`. Neither can consume `0.4.0` automatically.

## Lockfile policy

The future consumer update must change both `package.json` and
`package-lock.json` using ordinary npm resolution, for example:

```text
npm.cmd install @sukoyaka-dopeness/e2r-validator@^0.4.0
```

Lock integrity and resolved entries must be generated by npm, never hand-edited.

## Publication ordering

Decision: `VALIDATOR-PUBLISH-FIRST`.

1. Prepare Validator 0.4.0, changelog/version, and release gate.
2. Obtain explicit authorization, then push and publish Validator.
3. Verify the npm artifact and clean-install behavior.
4. Update LiaisonScape and NarrativeLine package manifests and lockfiles.
5. Run consumer gates and resume browser Formal Acceptance.

Consumers-first is rejected because clean installs cannot resolve an unpublished
production artifact. Permanent `file:`, branch, SHA, wildcard, or npm-link
dependencies are rejected for production.
