## Product boundary and application responsibilities

**Human-adopted direction:** combine general Entity editing and creative support in one application; do not prioritize EntityPool as a separate product now. General editing must remain useful without invoking a story method or imposing a fiction-specific Entity shape. People, organizations, places, documents, objects, and concepts are possible subjects. NarrativeLine remains the Event/time specialist, LiaisonScape the Relation graph specialist, and ParameterPlotter the Dimension comparison specialist. MotifMosaic would compose their information where appropriate rather than reimplementing each entire product or owning a parallel copy of shared facts.

**Human-stated modularization direction:** keep responsibilities distinct so bounded capabilities can later be reused by other E2R applications or hosts. Candidate separations include general Entity editing; Classification interpretation; Entity templates; method-specific creation and editing UI; story-structure reference and persistence; structural diagnostics; Dataset import/export; host-specific persistence; and inter-application handoff. These are responsibility seams, not a required package, repository, framework, dependency graph, or file layout. The accepted [application modularization decision](https://github.com/sukoyaka-dopeness/e2r-ai-knowledge/blob/main/decisions/application-modularization-and-incremental-extraction.md) calls for moderate, incremental boundaries and evidence before shared extraction. A future implementation should review its actual repository before deciding what to share. Generic semantic meaning and a method-specific editing experience need not have the same owner.

## Two working contexts and diagnostics

**Human-adopted direction:** combine construction and checking within the same working context rather than adding a separate third inspection view. Two primary views are a promising composition, with an Entity editing view and a conception view. The first could edit Classification, attributes, state, references, and profiles; the second could switch among tailored story-method interfaces. The exact screens, navigation, and components await UI experiments. Keeping selected Entity and in-progress context across view changes is desirable.

Diagnostics should appear near the relevant input when possible. Entity errors should also appear where that Entity is edited; Dataset-wide diagnostics might need a common surface. This is a UX direction, not a portable diagnostic schema or a choice of validator ownership. Structural checks and their source rules should be traceable. A reference that no longer resolves differs from an unfinished idea, an unspecified field, an intentional gap, or a work that departs from a theory. An unrepaid setup or unchanged character is not automatically an artistic defect. Rule-based assistance without required AI is a Human preference; aesthetic and literary judgment remains with the Human.

## Classification, roles, and templates

**Human-stated direction:** prepare Classification early enough to inform Entity editing, while keeping distinct: the Core Entity as an existence, a more detailed Classification, a role in a story or context, a content kind, and an editing template. “Person,” “knight,” “protagonist,” “article about a person,” and “edited with a person template” answer different questions. One Entity may have multiple classifications or templates. Display-label equality alone cannot establish shared semantic identity; stable concept identifiers may be needed for cross-application interpretation. A template guides editing and is not the sole authority for the meaning of stored information. Basic editing should remain available when an external vocabulary service cannot be reached.

The [Entity-linked responsibility audit](entity-portable-information-responsibility-audit-2026-10-07.md) already leaves Classification ownership, generic fields, Quantity, templates, provenance targets, and applicability unresolved; the [Semantic Vocabulary research](semantic-vocabulary-architecture.md) is a proposal, not an adopted contract. **Candidate sequence:** UI experiments may precede a portable template contract, but a full persistence contract should wait for evidence from a bounded vocabulary-fetch experiment and a separate Human design decision. This checkpoint adopts no Classification schema, term namespace, template representation, or mandatory field set.

## Story methods as structured authoring

**Human-stated UX direction:** translate story theory into inviting, method-specific structured inputs instead of a universal checklist. Illustrative candidates include Character Arc stages; Want/Need contrasts; opposing Entity goals; dilemmas with options and costs; Scene/Sequel goals, obstacles, results, reactions, and decisions; setup/payoff; misdirection and revelation; unequal knowledge; repeated or contrasting motifs; and structural roles of Scenes or Events. Correspondence, sequence, branching, and roles may be reusable patterns, but one common form or data type for every method is unselected. Users may combine methods and reference the same Entity or Event from more than one method. No theory is required of every user.

**Human-stated draft boundary:** a user should be able to outline a belief's initial state and changes after possible turning points without first creating empty Core Events. A conception note, Event candidate, and adopted Core Event should be distinguishable. A candidate becomes an established Core Event only after an explicit Human action; this does not impose a universal approval workflow or state machine. Linkage to an already existing Event should be possible to investigate. Temporal succession does not assert causation: a state change after Event A does not by itself mean Event A caused it. No Story Structure Extension or draft-storage contract is chosen.

**Human-required symmetry:** setup and payoff should not have different Event-link requirements merely because of their roles. The comparative recommendation is that Event linkage be optional for both, allowing unlinked drafts, multiple setups, and multiple payoffs for one story element. Stable identification is a promising way to associate them; string-label equality is insufficient to establish identity. Event association and the point at which a reader encounters a reveal are separate. The exact identity, cardinality, sequence, and persistence contract remain open.

Rule-based assistance might show correspondences, missing references, state sequences, choice/cost pairings, shared Event references, questions, and reference integrity. Each result should identify the authored information and rule behind it. This does not give mechanical diagnostics authority to grade a work's artistic quality.

## Journal and published content

The prospective Journal name remains open. The [Wiki/Blog/Journal research](future-application-ecosystem-session-ideas-checkpoint-2026-10-30.md#wiki--blog--journal-publication), [Personal Journal research](personal-journal-planner-and-multi-dataset-workspaces.md), and [Wiki research](e2r-wiki-portable-hosted-dataset-application.md) already explore publication and cross-entry navigation. **Candidate division:** MotifMosaic handles Entity/world/story conception, NarrativeLine Event/time work, Journal prose/articles/publication, LiaisonScape graph exploration, and ParameterPlotter Dimension assessment. Journal might also host fiction or screenplay prose. This is a responsibility comparison, not an adopted inter-app API or exclusive ownership map.

Prose presentation order can differ from in-world Event order. A Scene, chapter, article, and Event need not correspond one-to-one. A document may be an identified Entity distinct from its subject: Ellis the person, an article about Ellis, and an article titled “Ellis” could have separate IDs even when labels overlap. A profile that is just an editing view needs no extra profile Entity. Document identity and physical body storage are separate. A portable Extension carrying body content is an initial **candidate**; external Markdown and package-based carriage remain alternatives. This checkpoint chooses no Content Extension, format, asset policy, publication pipeline, or Handoff change.

## Vocabulary repository direction

**Human-adopted direction:** place E2R common vocabulary definition, validation, and distribution in an independent future repository, with **e2r-vocabulary** as a candidate name. The motivation is to avoid leaving experimental bulk vocabulary fetches in `e2r-spec` Git history. `e2r-spec` remains authority for specification, semantic contracts, and compatibility; a prospective vocabulary repository would own its common vocabulary artifacts and bounded experiments; a prospective MotifMosaic repository would own application implementation. This is a responsibility direction, not creation of those repositories or a finalized cross-repository layout.

External providers remain authoritative for their own vocabularies. Common E2R definitions, provider references, transient fetch caches, reproducible fixtures, and user vocabulary are different things. Large acquired datasets or caches should not be committed by default; fixture retention needs purpose, size, and licensing review. The [2026-10-28 Vocabulary checkpoint](future-e2r-applications-and-semantic-vocabulary-checkpoint-2026-10-28.md) keeps Dataset-local versus shared storage, identifiers, versioning, provenance, and provider choice open. The present repository direction does not settle those portable questions or authorize a fetch. Existing [Character Generator external-vocabulary research](../../applications/character-generator-app.md) and its Roadmap hold remain in force.

## Dependency sketch, evidence, and decisions still open

The session proposed a **conditional development path**, not a revised E2R-wide execution priority: this documentation checkpoint; independent vocabulary repository setup; MotifMosaic repository setup; a bounded Semantic Vocabulary fetch experiment; minimal Classification experiment; general Entity editing MVP; story-support MVP; and interoperability, automated testing, and Human acceptance. Repository setup is preferred before experimental fetches, but neither setup nor fetch is authorized by this documentation task. Character Arc, setup/payoff, and dilemma are illustrative first story-method candidates because they probe different input shapes; no MVP scope is selected.

**Human-stated verification interest:** make persistence and restoration of Entity data, Classification identity, draft story structure and incomplete ideas, setup/payoff symmetry, shared Event references, Dataset import/export, unknown Extension preservation, reference integrity, and UI regressions testable. Test tools and implementation structure are unselected. Automated pass does not establish that the authoring affordances feel natural; Human acceptance is a separate evidence gate.

Before implementation or a portable contract, resolve Classification ownership and identifiers; template and story-record persistence; draft/adoption lifecycle; content storage; exact application edit authority; external-vocabulary rights and cache/fixture policy; repository interfaces; host persistence; and the first bounded UI/prototype scope. No Cloudflare or other storage service, physical module split, fetch implementation, schema, Journal name, or launch schedule is selected.
