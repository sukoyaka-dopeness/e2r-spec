# E2R Session 0006

**Date:** 2026-07-26

## Summary

This session shifted the primary focus from the E2R specification itself to the first reference application, NarrativeLine.

Rather than introducing new Core features, the discussion clarified the boundary between the Core, Extensions, and Applications through practical application design.

Several architectural ideas also emerged for future versions of E2R.

---

# Decisions

## NarrativeLine MVP

The first NarrativeLine MVP will support the following workflow.

### New Dataset

The application provides two starting points:

- Open an onboarding sample dataset.
- Create an empty dataset.

The onboarding dataset exists only as a learning aid and is separate from normal editing.

---

### Event Creation

Events are created directly from Timeline View.

Workflow:

Timeline View

↓

New Event

↓

Event Detail

↓

Save

↓

Timeline View automatically scrolls to the newly created Event and moves keyboard focus to it.

---

### Event Editing

An Event may exist without any associated Entity.

Associating Entities is optional.

When an Entity is associated with an Event, the required Relation is automatically generated by the application.

Entity-to-Entity Relations are outside the MVP.

---

### Time Editing

Time is edited using separate fields.

Current fields:

- year
- month
- day

The data model should also support:

- hour
- minute
- second

These fields may initially be hidden behind a collapsed UI section.

---

### Timeline Ordering

Events are ordered using:

1. Temporal value
2. Temporal precision (coarser precision first)
3. Order
4. Event id

Examples:

1945

1945-08

1945-08-15

1945-08-15 12:00

1945-08-15 12:00:30

Events without temporal information appear after dated Events in the MVP.

Future versions may additionally support:

- Relative Time
- Causal ordering

---

### Saving

When saving:

- Order values may be regenerated.
- Unsupported Extensions should be preserved whenever possible.
- Existing dataset structure should be modified as little as possible.

When loading:

- Dataset validity should be verified.
- Unsupported Extensions should be ignored without failing.

---

# Architectural Decisions

## Applications Edit Only What They Understand

Applications should preserve unknown Extensions whenever possible.

Applications should edit only the Extensions they understand.

This principle was identified as an important guideline for all E2R applications.

---

## Reference Applications

NarrativeLine is considered a reference application rather than merely a consumer of the specification.

Reference applications validate practical usability and continuously provide feedback to the specification.

Examples already identified:

- NarrativeLine
- Relationship Graph

The specification and its reference applications are expected to evolve together.

---

## E2R as a Model of Change

The discussion reinforced that E2R is fundamentally a model of change rather than a model limited to historical timelines.

The same abstraction can describe:

- history
- stories
- software development
- dataset evolution
- UI state transitions
- workflows

This idea is considered a long-term architectural direction rather than part of the Core.

---

## Self-Descriptive Datasets

The possibility of describing the lifecycle of an E2R Dataset using E2R itself was discussed.

Examples include:

- dataset creation
- merge history
- migration history
- review history
- publication history

This concept is intentionally outside the current specification.

A future Dataset Provenance Extension may standardize this representation.

It was also recognized that:

- domain history
- dataset history

are fundamentally different concepts and should remain separate.

---

## Relationship Graph Notes

Several future design considerations for Relationship Graph were recorded.

Topics include:

- long Entity names
- Entity icons
- overlapping labels
- edge intersections
- multiple Relations between identical Entities
- automatic graph layout
- manual node positioning
- application-specific layout information

These ideas may eventually lead to application-specific layout Extensions but remain outside the current MVP.

# Open Questions

The following topics remain open.

- Whether `order` should eventually become independent of the History Extension.
- Standardization of Relative Time.
- Dataset Provenance Extension.
- Graph Layout Extension.
- Multiple application-specific presentation Extensions.
- Formal definition of the Core JSON data model.
